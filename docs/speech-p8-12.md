## หน้า 8 · Multi User (~1 นาที)

ต่อมาเป็นเรื่องที่หลายคนใช้งานไฟล์พร้อมกัน

ฝั่งซ้ายคือตัวอย่างที่เรียนในคาบ ใช้ mutex ตัวเดียว คือ buffer_lock ไม่ว่าจะ read หรือ write ทุกคนต้องรอกุญแจดอกเดียวกัน ถึงจะเป็นคนละไฟล์ก็ยังต้องรอ

ฝั่งขวาคือที่ fslek ใช้ เราใช้ inode_lock ของแต่ละไฟล์ ซึ่งข้างในเป็น rw_semaphore ถ้าเป็นการอ่าน จะใช้ inode_lock_shared ให้อ่านพร้อมกันได้หลายคน ถ้าเป็นการเขียน จะได้ทีละคน และที่สำคัญคือไฟล์ A กับไฟล์ B มีกุญแจของตัวเอง จึงไม่ต้องรอกัน

แถวกลางตอบคำถามว่า ทำไมเรา copy ข้อมูลระหว่างที่ถือ lock อยู่ ทั้งที่ในคาบแนะนำให้ copy ข้างนอก มีเหตุผลสามข้อ

- ข้อแรก buffer ถูกย้ายได้ ตอนขยาย fslek_reserve จะจองก้อนใหม่แล้ว kvfree ก้อนเก่าทิ้ง ถ้า copy นอก lock อาจไปอ่านก้อนที่คืนไปแล้ว
- ข้อสอง ไม่เปลือง RAM ถ้าจะ copy นอก lock ต้องมี buffer ชั่วคราว ไฟล์ 64 MiB ก็จะใช้ RAM สองเท่า
- ข้อสาม ไม่เกิด lock ซ้อนตัวเอง เพราะ fslek ไม่มี mmap จึงไม่มี page fault ที่วนกลับเข้ามาหา fslek ระหว่างถือ lock

ผลทดสอบ ให้ 8 process เขียนไฟล์เดียวกัน คนละ 1000 บรรทัด ได้ครบ 8000 บรรทัด และให้ 4 process อ่านไปพร้อมกับที่ไฟล์โตถึง 16 MiB ก็อ่านถูกทุกครั้ง ต้องบอกตรงๆ ว่านี่เป็น smoke test ยังไม่ได้พิสูจน์ว่าไม่มี race ในทุกกรณี

## หน้า 9 · RM, MV, Size Limit, Stat (~1 นาที 15 วินาที)

หน้านี้เป็นงานเสริมสี่อย่างที่เราทำเพิ่มจากโจทย์

**rm** คือการแกะป้ายชื่อออก simple_unlink ทำให้ nlink เป็น 0 ทันที แต่ถ้ายังมีคนเปิดไฟล์ค้างอยู่ ข้อมูลยังไม่หาย ยังอ่านเขียนผ่าน fd เดิมได้ จนคนสุดท้ายปิดไฟล์ evict_inode จึง kvfree buffer ทิ้ง ส่วน rmdir โฟลเดอร์ที่ยังไม่ว่าง จะได้ ENOTEMPTY

**mv** เปลี่ยนแค่ป้ายชื่อ ใช้ simple_rename ย้าย hello.txt ไปเป็น docs/renamed.txt แล้วเลข inode ยังเป็น 47880 เหมือนเดิม แปลว่าไม่ได้ copy เนื้อหาเลย

**size=10M** คือจำกัดขนาดของทั้ง mount ทุกครั้งที่จะจอง buffer ต้องผ่าน fslek_charge ก่อน มีสามกรณี ถ้าโควตาเหลือพอก็ได้ครบและขยายเท่าตัวตามปกติ ถ้าเหลือน้อยกว่าที่ขอแต่ยังพอเขียน ก็ได้เท่าที่เหลือ ถ้าไม่พอจริงๆ ได้ ENOSPC หรือ No space left on device ถ้าไม่ใส่ size= จะใช้ครึ่งหนึ่งของ RAM เหมือน tmpfs

**/proc/fslek** ดูตัวเลขสดได้ทันที มีสี่ค่า คือ files, directories, bytes และ grows นับด้วย atomic_long_t แทน mutex เพราะแต่ละค่าไม่เกี่ยวกัน ไฟล์ต่างกันจึงไม่ต้องรอกัน

ทั้งสี่อย่างมีทดสอบใน test_edge.sh รวม 131 เคส

## หน้า 10 · Demo (~3 นาที)

ต่อไปจะเดโมให้ดูครับ/ค่ะ รัน sudo bash tests/demo.sh แล้วกด Enter ทีละขั้น

*(ขั้น 1-3 build และโหลด module ผ่านเร็วๆ)*

- **ขั้น 4** mount แล้ว findmnt เห็นชนิดเป็น fslek และโฟลเดอร์ว่าง
- **ขั้น 6** เขียน ต่อท้าย แล้วเขียนทับ cat ดูทีละรอบ ข้อมูลถูกต้อง
- **ขั้น 9** สร้างโฟลเดอร์ซ้อนกันหลายชั้น ls -laR เห็นครบ
- **ขั้น 10a** ลองสร้างไฟล์ซ้ำได้ File exists, rmdir โฟลเดอร์ไม่ว่างได้ Directory not empty และ mv แล้ว ls -i ดูเลข inode ยังเท่าเดิม
- **ขั้น 10b** mount ใหม่ด้วย size=10M มีไฟล์จองอยู่แล้ว 8 MiB เขียนเพิ่มได้อีก 2 MiB แล้วขึ้น No space left on device พอ rm ออก df ก็เห็นพื้นที่กลับมา
- **ขั้น 10c** ดู /proc/fslek ก่อนเขียน หลังเขียน 1 MiB bytes เพิ่ม 1,048,576 และ grows เพิ่ม 5 พอลบไฟล์ ค่า bytes ก็กลับเท่าเดิม
- **ขั้น 11** umount แล้ว mount ใหม่ โฟลเดอร์ว่างเปล่า เพราะข้อมูลอยู่ใน RAM

*(ถ้า VM มีปัญหา ให้ชี้ภาพบนสไลด์แทน หรือเปิดวิดีโอสำรอง)*

## หน้า 11 · ผลลัพธ์ (~1 นาที)

ฝั่งซ้ายคือการทดสอบ เรามีสองสคริปต์ test_mvp.sh ตรวจ 7 operation ตามโจทย์ ผ่าน 31 จาก 31 และ test_edge.sh ไล่กรณีขอบกับงานเสริม ผ่าน 225 จาก 225 รวมเป็น 256 เคส ผ่านทั้งหมดบน kernel 6.8 และ dmesg ไม่มี Oops เลย สิ่งที่ยังไม่ได้ทดสอบคือกรณี kvzalloc ล้ม memory leak ฝั่ง kmalloc และ kernel 7.0

ฝั่งขวาคือความเร็ว วัดไฟล์ 64 MiB เอาค่ากลางจาก 15 รอบ หน่วยเป็น MiB ต่อวินาที แท่งยิ่งยาวยิ่งเร็ว สีดำคือ fslek เทียบกับ ramfs สีเทา และ tmpfs สีขาว

- เขียนก้อน 1M เร็วกว่า ramfs 1.7 เท่า
- อ่านก้อน 1M เร็วกว่า 1.6 เท่า
- เขียนทีละ 4K เร็วกว่า 1.7 เท่า
- แต่อ่านทีละ 4K ถือว่าไม่ต่าง เพราะเวลาส่วนใหญ่หมดไปกับ system call

เหตุผลที่น่าจะเป็นคือ fslek copy ลง buffer ก้อนเดียว ไม่ต้องจองทีละหน้าใน page cache แต่เรายังไม่ได้ profile และต้องยอมรับว่า fslek ทำงานน้อยกว่า เพราะไม่มี mmap และไม่มี swap

## หน้า 12 · ข้อจำกัดและสรุป (~40 วินาที)

สุดท้ายคือข้อจำกัด ทุกแถวมีหลักฐานจากเดโมหรือ test_edge.sh

- **ปรับต่อได้** มีสองแถวบน
  - RAM ส่วนเกิน ไฟล์ 5 MiB จองจริง 8 MiB เพราะขยายเท่าตัว และคืนก็ต่อเมื่อ truncate เป็น 0
  - write ก้อนใหญ่กว่าที่เหลือจะล้มทั้งก้อน ไม่เขียนบางส่วน
- **นอกขอบเขตโจทย์** มีสามแถว ได้แก่ ln กับ symlink, mmap และ O_DIRECT
- **ตั้งใจ** มีสองแถว ได้แก่ ไฟล์ใหญ่สุด 64 MiB กับข้อมูลหายหลัง umount เพราะอยู่ใน RAM
- **kernel 7.0** โค้ดเตรียมไว้แล้ว แต่ยังไม่ได้ build จริง *(ลบข้อนี้ถ้าทดสอบผ่านก่อนพรีเซนต์)*

สรุปคือ เราใช้ของที่ VFS มีให้มากที่สุด เขียนเองแค่ส่วนเก็บข้อมูลกับโควตา และทุกผลลัพธ์รันซ้ำได้จากสคริปต์ ทั้ง 256 เคสและเดโม 14 ขั้น
